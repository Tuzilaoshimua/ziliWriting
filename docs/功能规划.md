## 1. 总体原则

1. **本地优先**：不新增后端服务；所有数据留在本机 SQLite / 文件系统。
2. **不引新依赖优先**：关系图、时间线、统计图用原生 SVG/CSS 实现；确需依赖时单独说明理由。
3. **可溯源**：任何 AI 派生内容都要能点回原文证据（章节 + 引文 + 节点）。
4. **派生优先、手绘次要**：可视化默认从已确认记忆派生；确实需要人工补充时，走记忆候选（draft → confirm）流程，避免绕开正典。
5. **渐进增强**：新表只加不改；老数据零迁移成本；浏览器模式（web fallback）功能不劣化。
6. **每阶段可交付**：每完成一个里程碑都能独立使用，并通过 `tsc -b` + `vite build` + `cargo check`。

## 3. 详细设计

### F1 人物关系图

**目标**：把"谁和谁是什么关系"从文字列表变成可筛选、可溯源的网络图，长篇（20+ 人物）也能快速看清结构。

**用户故事**
- 作为作者，我想一眼看出主角的关系网，找出被冷落的角色。
- 作为作者，我想确认"这两人到底有没有在正文里建立关系"，并跳回原文核对。

**数据来源（现有，不新增存储）**
- 节点：`buildCharacterMemoryProfiles(project, bundles)` 返回的人物档案（别名已合并）。
- 边：人物档案里的 `relationships: CharacterRelationshipMemory[]`（title / counterparts / value / chapterId / candidate）。
- 过滤依据：关系候选的 `metadata.validFromChapterId` / `validToChapterId`、`chapterId`，以及章节顺序索引。

**派生规则**
1. 节点 id 用档案 id；显示名默认 `name`，悬停显示别名。
2. 边只连"两端都能对上档案"的关系；`counterparts` 依次做归一化匹配（复用 `matchingNameId` 的归一化规则）。
3. 同一条记忆（同一 `candidate.id`）只产生一条边；双向关系去重（source < target）。
4. 关系分类（仅用于配色，不影响数据）：按 title/detail 关键词粗分
   - 亲缘：父/母/子/女/兄/弟/姐/妹/夫妻/婚约/血亲
   - 情感：爱/喜欢/暗恋/情人/恋人
   - 同盟：友/盟/同门/师徒/主仆/搭档/合作
   - 敌对：敌/仇/对立/追杀/背叛/宿敌
   - 交易：雇佣/债/契约/交易/买卖
   - 其他：未知
5. 节点大小 = `evidenceCount` 的对数缩放；节点颜色 = 首次出场卷（卷多时按色相环分配）。

**过滤**
- 全书 / 当前卷 / 截至当前章（三者互斥，默认"截至当前章"）。
- 可选"只看已确认"（当前数据源本身只取 confirmed）。
- 搜索框复用现有 `memorySearch`：命中节点名/别名则高亮并聚焦。

**交互**
- 拖拽节点（拖动期间暂停布局计算）；双击节点 = 只显示该节点的邻居。
- 点击节点：右侧显示该人物的迷你档案（身份/当前状态 Top3 + 关系数）。
- 点击边：显示证据（章节名 + 引文），可"查看原文"跳转（复用 `openAnswerCitation`）。
- 悬停边/节点：高亮。
- 缩放：滚轮缩放 + 拖拽画布平移（限制 0.4x–3x）。
- 空态：无关系时提示"先分析并确认关系资料"。

**布局**
- 纯前端力导向（Fruchterman–Reingold 简化版）：斥力 + 边弹簧 + 向心力，迭代 300 次后固定；节点数 > 80 时降为环形布局（避免卡顿）。
- 布局结果只存在内存；切换过滤重算。确定性：以节点 id 排序初始化，避免每次抖动。

**UI 位置**
- 故事记忆 → 人物：在现有"档案/状态/关系/轨迹"标签页上方加视图切换：`列表 | 关系图`（默认列表，保持现有习惯）。
- 关系图占满人物详情区；目录栏保留（点人物 = 聚焦节点）。

**边界与风险**
- 人物过多导致拥挤 → 默认"截至当前章" + 邻居聚焦 + 80 节点阈值降级环形。
- 关系数据稀疏 → 图会稀疏，属正常；空态文案解释如何产生数据。
- 参与人名字对不上档案（"那个男人"）→ 匹配失败的关系丢弃并在角标显示"未匹配 N 条"，避免脏边。
- 不做手动自由连线（二期可加"补一条关系"，写入记忆候选，需确认）。

**验收标准**
- 给定 ≥3 人的已确认关系数据，图中节点/边数量与档案一致（允许"未匹配"计数说明）。
- 点边能看到该关系的章节与引文，并能跳转到原文。
- 切换"当前卷/截至当前章"后，边集合按 validFrom/validTo 正确收敛。
- 80 人规模下渲染 < 100ms（无长时间卡顿）。
- `tsc -b` 通过。

**工作量**：约 1 个开发轮次（数据模块 + 布局 + UI + 样式）。

### F2 人物时间线可视化

**目标**：把人物状态变化（`CharacterStateSnapshot`：aspect / value / previousValue / chapterId / storyTime）画成横向时间轴，看清"谁在第几章变成了什么"。

**数据来源**：`CharacterMemoryProfile.timeline`，字段已含 `storyTime` 与 `validFrom/validTo`。

**设计**
- 视图：故事记忆 → 人物 → 新增标签 `时间轴`（与"关系图"并列，共用视图切换）。
- 横轴：章节顺序（默认）或故事时间（`storyTime` 存在时切换，做字符串排序 + 精度提示）。
- 行：每个主要人物一条泳道；节点 = 一次状态快照，颜色按 aspect 分类（身份/位置/健康/立场/关系…）。
- 点击快照：显示 previousValue → value 对比 + 证据跳转。
- 过滤：时间范围、aspect 类别、人物搜索。
- 复杂度控制：默认只显示选中人物（或 Top 5 证据数人物）。

**验收标准**
- 一个拥有 ≥2 次状态变化的人物，时间轴顺序与章节顺序一致。
- 快照可点开看到"由 X 变为 Y"和原文证据。
- 切换章节轴/故事时间轴不崩溃；`storyTime` 缺失时有兜底文案。

**工作量**：约 0.5 个轮次（复用 F1 的 SVG 视图框架）。

### F3 写作统计看板

**目标**：日更字数、连续写作天数、各章耗时、目标完成度回填，帮助长期连载作者掌握节奏。

**新增数据（SQLite migration 24）**

```sql
CREATE TABLE IF NOT EXISTS writing_sessions (
  id TEXT PRIMARY KEY NOT NULL,
  project_id TEXT NOT NULL,
  chapter_id TEXT,
  started_at INTEGER NOT NULL,
  ended_at INTEGER NOT NULL,
  words_added INTEGER NOT NULL DEFAULT 0,
  words_removed INTEGER NOT NULL DEFAULT 0,
  active_ms INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_writing_sessions_project ON writing_sessions(project_id, started_at);
```

- 采集：编辑器已有保存/字数统计链路；在保存时按"本次增量"累加到当前会话（30 分钟无操作即结束会话）。
- 只存增量，不回算历史；历史章节字数从 `plainText` 现算。
- web fallback：`webDatabase` 同结构对象存储；无 SQLite 时退化为 localStorage 日聚合（仅当日/近 30 天可用）。

**指标**
- 今日 / 本周 / 本月新增字数；
- 连续写作天数（按"当日新增 > 0"计）；
- 近 30 天日更柱状图（SVG，不引图表库）；
- 各章累计字数与书写耗时（会话求和）；未记录耗时的显示"—"；
- 目标完成度：复用 `preferences.wordGoal`（本章目标），显示今日/本章完成百分比；
- 全书记录：总字数、已完成章数（正文非空）、平均章字数。

**UI 位置**：新入口"写作统计"，放侧边/顶栏统计区（现有字数显示旁），点击打开面板；不做独立页面以免打断写作流。

**验收标准**
- 连续输入 200 字后，今日字数增加 200（容差 ±2）。
- 关闭重开应用后统计数据仍在。
- 换章不串数据（按 chapter_id 隔离）。
- 删除章节后统计不报错（会话保留，展示时忽略已删除章节）。

**工作量**：约 1 个轮次。

### F4 大纲节点 ↔ 章节显式绑定

**目标**：让"大纲节拍 → 已写章节"从关键词猜测变成作者确认的确定性映射，覆盖度检测不再误判。

**数据（SQLite migration 25）**

```sql
CREATE TABLE IF NOT EXISTS outline_chapter_links (
  project_id TEXT NOT NULL,
  node_id TEXT NOT NULL,
  chapter_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (project_id, node_id, chapter_id)
);
CREATE INDEX IF NOT EXISTS idx_outline_links_project ON outline_chapter_links(project_id);
```

**设计**
- 大纲面板每个 chapter/scene 节点增加"绑定章节"选择器（多选）。
- 覆盖度算法升级：节点绑定的章节一律视为已覆盖（`status='covered'`，标记"已绑定"）；未绑定时回退现有关键词匹配，并标注"自动推断"。
- 报告里区分"已绑定 / 自动推断 / 未覆盖"，作者可一键"采纳推断"写入绑定。
- 章节删除时清理孤立绑定（惰性清理：读取时过滤不存在的 chapterId）。

**验收标准**
- 绑定后覆盖度结果稳定（与正文措辞无关）。
- 解除绑定后回退到关键词判定。
- 采纳推断后重新检测结果不变。
- 老项目（无绑定时）行为与现在一致。

**工作量**：约 0.5–1 个轮次。

### F5 按任务分模型

**目标**：不同任务用不同模型：记忆提取/摘要用便宜快模型，草稿/改稿用强模型。

**数据（preferences 扩展，不改表）**
- `AiSettings` 增 `taskRoutes: Record<AiTaskType, { providerId, baseUrl, model }>`（无条目 = 用全局配置）。
- 任务类型沿用现有 `metadata.taskType`（如 agent / review / style / memory-extract / outline / anti-ai 等，以 `src/ai` 现有取值为准）。

**设计**
- `client.ts` 解析：请求前按 `metadata.taskType` 查 `taskRoutes`，命中则整体切到该路由的 provider / baseUrl / model；未命中沿用全局配置。
- 路由到用户 API 时，密钥按端点从系统凭据库取回（内置服务模式下内存里没有用户密钥）；取不到则回退全局，避免把请求打到无凭据的端点上。
- 设置 → AI「按任务指定模型」：任务下拉 + 接口来源（跟随全局 / 内置服务 / 用户 API）+ 该任务的模型与端点。
- 兼容：旧版只存模型名的 `taskModels` 在读取时自动迁移为「用户 API + 最近保存的自定义端点」。

**验收标准**
- 配置后，指定任务的请求体确实使用了覆盖模型（可用本地日志/网络面板验证）。
- 未配置的任务仍用全局模型，行为不变。
- 清空某项即恢复全局模型。

**工作量**：约 0.5 个轮次。

### F6 敏感词与合规自查

**目标**：上架/投稿前本地自查，减少平台审核踩雷，不做道德审查。

**设计**
- 内置基础词表（分级：提示/警告/高风险），支持用户自定义词表（设置里导入/编辑，存 preferences 或独立文件）。
- 扫描范围：当前章 / 全书已写章节；输出命中列表（词、章节、上下文 ±20 字、偏移）。
- 展示：类似 review issue 的面板，可跳到正文位置；可导出 `.md`/`.txt` 报告。
- 纯本地，不联网，不上报；明确提示"不替代平台官方审核"。
- 与"去 AI 腔"检查并列放，互不干扰。

**验收标准**
- 含自定义词的章节能被检出并定位。
- 导出报告包含章节名+上下文。
- 空词表时不报错并提示导入。

**工作量**：约 0.5 个轮次。

### F7 分享稿与批注

**目标**：把稿子发给编辑/beta 读者，收回结构化批注。

**一期：分享稿导出**
- 导出只读稿：HTML（单文件，内嵌样式，无编辑能力）+ 可选 PDF（复用现有打印链路）。
- 每个段落带稳定锚点 `data-anchor="ch-<chapterId>-p-<index>"`。

**二期：批注包**
- 格式 `.zilicomments.json`：
  ```json
  { "version": 1, "projectId": "...", "projectTitle": "...",
    "comments": [{ "chapterId": "...", "anchor": "ch-...-p-12", "quote": "...",
                   "comment": "...", "author": "...", "createdAt": 0 }] }
  ```
- 导入：按 anchor 定位，导入后进入"批注"侧栏（新 DB 表或 localStorage，建议新表 migration 26）。
- 冲突：anchor 找不到时按 quote 在全章搜索兜底，仍失败则归入"未定位"。
- 不做实时协作/账号体系。

**验收标准**
- 导出的 HTML 在浏览器打开可读、分章。
- 导入批注后能在对应段落旁看到，点击可跳转。
- 未定位批注单独分组，不丢失。

**工作量**：约 1.5 个轮次（一期 0.5，二期 1）。

### F8 跨设备同步（网盘文件夹）

**目标**：用用户已有的网盘（OneDrive/坚果云/Nextcloud 本地同步目录）做项目级同步，不自建服务。

**设计**
- 设置里指定"同步目录"；每项目写 `<projectId>/project.zili.sync` + `manifest.json`（revision、updatedAt、deviceId、size、hash）。
- 触发：手动"立即同步" + 定时检测（启动时、每 5 分钟）比较远端 manifest 的 revision/updatedAt。
- 拉取：远端较新 → 提示"发现较新版本"，用户确认后备份本地再覆盖。
- 冲突：revision 相同但 hash 不同 → 生成 `project.conflict-<timestamp>.zili.sync`，不覆盖。
- 安全：不做端到端加密（网盘自带），文档里明确风险；文件名/路径做长度与非法字符校验（复用 Rust 备份侧校验）。

**验收标准**
- 两台设备（或两个目录模拟）间可完成"改 → 同步 → 拉取"。
- 冲突时不丢数据，双方文件都在。
- 同步目录不可写时给明确错误，不影响本地保存。

**工作量**：约 2 个轮次（涉及 Rust 命令 + 冲突策略）。

### F9 命令面板与快捷键

**目标**：键盘操作全覆盖，降低对鼠标的依赖。

**设计**
- `Ctrl/Cmd+K` 打开命令面板：搜索命令（复用现有 `pattern → run` 命令注册表），回车执行。
- 命令可注册快捷键（默认一套，如 Ctrl+Shift+F 专注、Ctrl+Shift+B 备份），支持在设置里重绑（preferences 存 `keymap`）。
- 冲突检测：重复绑定给出警告。

**验收标准**
- 面板可搜索并执行至少 15 条命令。
- 自定义快捷键重启后生效。
- 冲突绑定有提示且不崩溃。

**工作量**：约 1 个轮次。

## 4. 数据与存储约定

1. **SQLite**：只加表/加列，不改名；新表从 migration 24 起递增；每张新表带 `project_id` 与查询索引；删除项目时清理（复用现有删除流程）。
2. **Web fallback**：`webDatabase.ts` 的对象存储按表名对应；无法实现的指标（如跨设备）在浏览器模式隐藏入口而非报错。
3. **localStorage**：偏好类配置用 `zili-writing-preferences-v1` 扩展字段；独立模块用 `zili-<domain>-v1`。
4. **文件格式**：批次文件统一带 `version` 字段，便于未来升级。
